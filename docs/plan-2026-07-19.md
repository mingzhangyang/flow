# 评估问题处置计划（2026-07-19）

> 来源：2026-07-19 项目评估（`npm run check` 全绿，172/172）。评估结论：架构与工程质量无虞，
> 起始风险集中在**运维面**（真机未验证、keystore 未备份、6 个 commit 未推送）与**市场面**（零真实用户）。
> 本计划按优先级把问题变成可执行、有完成判据的动作。执行者标注：【用户】需要真人/账号/真机，
> 【Agent】可在会话内完成。
>
> Constitution: C5（提醒必须可靠）、C6（成果不可丢失）、C10（可追溯的工程流程）、
> E6（医疗场景描述性、非处方性）。

---

## 执行前基线（已准备）

- [x] **RC 可追溯门槛**：真机结果必须绑定唯一 commit SHA + EAS build ID；代码、依赖或原生配置
      发生变化后，旧结果自动失效，必须重建并重测。RC 后允许只追加发布证据文档，并由
      `scripts/verify-rc-scope.sh <RC_SHA>` 自动证明范围。流程见 [`release.md`](./release.md)「冻结候选版本」。
- [x] **Android 验证工具**：[`android-reminder-check.sh`](../scripts/android-reminder-check.sh)
      提供设备快照、普通进程死亡、Doze 进出、设置页跳转和显式受保护的 force-stop / 重启命令；
      [`android-reminder-test-results.md`](./android-reminder-test-results.md) 作为结果记录模板。
- [x] **平台范围拆分**：本计划 P1 是 Android RC 门槛；iOS 在产生可安装构建后走独立门槛，
      未验证前不得进入 TestFlight / App Store 发布列车。
- [x] **Android force-stop 语义澄清**：`am force-stop` 会把包置于 stopped state，重新打开前
      通知不应被期待送达；它是平台边界测试，不是“后台存活”通过项。

## P0 — 止损：保住已有成果（今天，约 30 分钟）

起始风险：分支 `chore/eas-project-link` 领先 main 6 个 commit 且**尚无远端 upstream**；
本计划、交接快照与真机验证材料尚未入库；keystore 只存在于 EAS 云端。一次磁盘/账号事故
即可能造成不可逆损失。

- [x] **① 准备材料入库**【Agent】：提交本计划、`docs/release-status.md`、真机结果模板、adb 辅助脚本
      以及同步修改的发布文档；提交前用 `git status --short` 确认没有相关文档/脚本仍未跟踪。
      提交信息标注 `Constitution: C5, C6, C10; E6`。
- [x] **② 分支推远程做异地备份**【Agent】：`git push -u origin chore/eas-project-link`。
      **push ≠ merge**——备份不必等真机验证，合并才等（见 P2）。
- [x] **③ keystore 备份**【用户，约 15 分钟】：按 [`keystore-backup.md`](./keystore-backup.md) 全流程：
      expo.dev 控制台下载 `.jks` + 抄录三组值（keystore 密码 / key alias / key 密码）→ 存 KeePassXC
      → `.kdbx` 异地副本。完成判据见该手册「完成判据」节；`.jks` 绝不入库。

**出口判据**：三项全勾。此后任何单点故障（本机盘坏、EAS 账号异常）都不再致命。

## P1 — Android 真机验证核心承诺（本周内，1–2 小时 + 一夜观察）

这是全项目当前**价值最高**的一步：产品的核心承诺（到点提醒，尤其服药）依赖 Doze、
厂商后台查杀、精确闹钟授权等**任何测试都无法覆盖**的真机行为。清单全绿之前，
「提醒不断档」只是假设。

- [x] **④ 冻结并构建 Android RC**【Agent】：按 [`release.md`](./release.md)「冻结候选版本」执行
      `npm run check`、`npm run test:e2e`、`npx expo-doctor`，记录 HEAD SHA，再从**该 SHA**生成
      EAS preview APK；把 SHA、build ID、产物链接和 APK SHA-256 写入 `release-status.md` 与结果表。
- [ ] **⑤ 安装精确 RC**【用户】：只安装步骤 ④ 记录的 APK，并核对应用版本/构建记录；
      旧的 `21452e4` APK 可用于试装，但不能作为当前分支的验收证据。
- [ ] **⑥ 过 Android 真机验证清单**【用户，Agent 辅助】：逐项走 [`release.md`](./release.md)
      「Android RC 验证」，用 [`android-reminder-check.sh`](../scripts/android-reminder-check.sh)
      辅助，并填写 [`android-reminder-test-results.md`](./android-reminder-test-results.md)。
      普通进程死亡应继续提醒；force-stop 预期重新打开前不提醒，两者不得混为同一项。
- [ ] **⑦ 处置结果**【Agent】：失败项逐条修复；任何影响代码、依赖或原生配置的修复都回到步骤 ④，
      重新构建并至少重跑受影响项。全过后更新 `release-status.md`。国产 ROM 一台若暂无设备可延后，
      但必须在结果表与快照中显式标注为未验证。

**出口判据**：Android 必测项全绿（或仅剩国产 ROM 项且已标注）；结果表的 RC SHA 与待合并 HEAD
完全一致，或 `verify-rc-scope.sh` 证明其后只有发布证据文档；force-stop 项符合“重新打开前不保证送达”
的平台预期，而不是要求通知响。

## P2 — 合并与发布列车（P1 通过后）

- [ ] **⑧ 合并入主干**【Agent】：先确认 CI 全绿、工作树干净、当前 HEAD 等于结果表 RC SHA，
      或 `verify-rc-scope.sh <RC_SHA>` 通过；
      再同步 `origin/main` 并执行 fast-forward-only 合并与 push。若 main 已前进或 SHA 不一致，
      停止合并并重新评估/验证，不能沿用旧结果。
- [ ] **⑨ 商店前置**【用户为主】：按 [`release.md`](./release.md)「商店提交前置」——
      隐私政策上线（Cloudflare Pages）、真机重截商店截图、Play Console internal testing、
      健康类内容与 AI 数据共享申报（口径见 [`store-listing.md`](./store-listing.md)）。

> iOS 不借用 Android 的结果。产生 iOS RC 后，必须记录独立 SHA/build ID，验证权限时机、
> 普通终止后的本地提醒、重启/系统升级边界、拒绝权限与设置恢复，再进入 TestFlight / App Store。

## P3 — 真实用户验证（发布后立即开始；最重要的长期项）

评估指出：工程轴已远超验证轴。下一批投入应流向「有人真的在用吗」，而不是更多代码。

- [ ] **⑩ 自用 dogfood**【用户】：先用非医疗日程（作息）和顺序型（咖啡/烹饪）建立基线；
      若用于真实服药，只能作为既有提醒方式的**并行辅助**，不得替代医嘱、药盒或原提醒。
      漏报、误报、烦人之处即时记录；出现漏报即停止把它用于健康关键提醒，先处置问题。
- [ ] **⑪ 1–3 个真实用户**【用户】：创始场景可优先邀请真正需要按时服药的人，但必须知情说明
      “内测、非医疗建议、不可作为唯一提醒”，不得建议改变药物或时间安排，也不收集不必要的健康数据。
      观察他们卡在哪，特别是**分享/导入**环节（当前是「整段 JSON 文本走分享面板」，
      对非技术用户摩擦最高）。
- [ ] **⑫ 分享摩擦的候选方案（先证明需求，再动手，C0）**：若 ⑪ 证实分享是真实需求，
      候选为 **QR 码承载 flow JSON**——离线、无服务器、仍是开放格式（追溯 C6/E5）。
      实现前先测真实 Flow 的编码体积并定义单码容量/失败回退；在此之前**不做**，避免为想象中的用户造功能。

## P4 — 代码小项（顺手修，不阻塞 P0–P2）

评估中的次要发现，按「值得修 / 等信号 / 明确不修」三档：

- [ ] **值得顺手修**：`ScheduleScreen` 登记 effect 依赖 `flow` 对象身份 → 改依赖 `flow.id`
      （现状幂等无害，只是重渲染时白跑一次登记）。
- [ ] **值得顺手修**：装 `expo-system-ui`，让 Android 原生层深浅色跟随生效
      （prebuild 警告，见 release-status「已知但不阻塞准备阶段的事项」；应用内 `useColorScheme` 不受影响）。
- [ ] **等信号再做**：打卡宽限期 120 分钟硬编码（`ScheduleScreen` 的 `GRACE_MINUTES`）→
      升为 Flow 级可选字段（加法演进 E5）。触发条件：真实用户反馈宽限期不合适。
- **明确不修（记录理由）**：Storage 全键扫描（个人规模无感，代码内已注明取舍）；
  手写状态机导航（8 屏内仍是 Constraint 0 的正确选择，屏数继续增长再议）。

**P4 的 C9 预判**：effect 依赖修正属于 UI 层且不改接口；`expo-system-ui` 属于 App/原生集成边界，
不进入 Domain/Runtime。宽限期一旦升级为 Flow 字段，则属于 Domain Model + UI 的加法 schema 演进，
届时必须同步 architecture、迁移/校验与契约测试，不能只改 `ScheduleScreen` 常量。
