# 核心宪章

## Constraint 0 —— 概念纯粹性高于一切

**永远不要为了增加功能而损害概念的纯粹性。**

很多优秀的软件不是死于技术，而是死于概念不断膨胀——待办、日历、笔记、聊天、项目管理全塞进来之后，用户再也无法用一句话解释它是什么。

Flow 必须始终能用一句话定义：

> **Flow 是一种用于表达、执行和共享「时间模式（Temporal Pattern）」的载体。**

如果一个新功能不能增强这个定义，只是增加复杂度，它就不应该进入产品。这条约束凌驾于其余所有约束之上，其余约束都是为它服务的。

---

## 一、使命（Mission）

帮助人们把**任何具有时间结构的知识**，转化为可执行、可复用、可共享的 Flow。

我们不是帮用户"设置计时器"，而是帮用户**把经验变成可以运行的时间模式**。一个好的 Flow，不只指导今天的自己，也帮助未来的自己，甚至帮助他人。

## 二、愿景（Vision）

Flow 应成为**时间知识的通用载体**。

- PDF 保存文档，Excel 保存数据，Markdown 保存文本，Mind Map 保存思维结构；
- **Flow 保存的是「时间组织起来的知识」（Knowledge Organized in Time）。**

任何具有时间结构的经验，都应该能被表达、运行、分享和改进。

---

## 三、第一原则（First Principles）

**C1 — Flow 是第一公民，不是 Timer。**
系统围绕 Flow 构建，Timer 只是运行时。每个设计先回答"这是否让 Flow 更容易表达？"，而不是"这是否让 Timer 更强？"。

**C2 — Flow 是知识，而不是配置。**
用户创建的不是一组参数，而是一份可以阅读、可以理解、可以分享的知识。"法压咖啡"应该是"加入热水 → 浸泡 4 分钟 → 搅拌 → 等待 30 秒 → 压杆"，而不是"5min / 30sec / 2min"。

**C3 — 节点表达的是事件，而不是时间。**
不要让用户想"等待多久"，而是想"下一件事情是什么"。时间只是事件之间的一种关系。
（注：并非所有事件关系都是"接续"，见 `01-domain-model.md` 的两种时间拓扑。）

**C4 — 运行必须比编辑更简单。**
编辑可以复杂，运行必须极简。运行界面要做到"打开即可开始"，全程用户几乎不用思考 UI。

**C5 — Flow 必须能够暂停。**
现实不是程序：实验室有人敲门、孩子突然哭、电话来了。Flow 必须允许暂停、恢复、跳过、回退、等待确认。**现实永远优先。**

**C6 — Flow 永远属于用户。**
Flow 必须能导出、备份、同步、分享，采用开放格式。永远不要把 Flow 锁在服务器里。模型可以换，平台可以换，**Flow 不应消失**。

---

## 四、Flow 不是什么（Anti-Goals）

宪章的价值在于能替我们说"不"。以下清单让任何人/Agent 都能具体地驳回功能膨胀：

- Flow **不是**待办清单（To-do）。
- Flow **不是**日历（Calendar）。
- Flow **不是**笔记（Notes）。
- Flow **不是**项目管理（Project Management）。
- Flow **不是**聊天工具（Chat）。

Flow 只做一件事：**表达、执行、分享「时间模式」。** 任何把它推向以上形态的需求，默认拒绝，除非能证明它增强了 Constraint 0 的一句话定义。
