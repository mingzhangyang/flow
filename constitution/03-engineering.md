# 工程约束

分两类：**不可违反的原则**，和**可随经验修订的实现选择**。

## A. 不可违反的原则

**E1 — Flow 是声明式的（Declarative）。**
Flow 只描述"应该发生什么"，不描述"如何执行"。执行细节属于 Runtime，不属于定义。

**E2 — Runtime 是无状态或最小状态的。**
Runtime 根据「Flow 定义 + 当前时间 + Run 的执行记录」恢复运行，而不依赖大量隐式内存。杀掉进程再拉起，应能从记录精确恢复。

**E3 — 时钟是显式输入，不是环境隐读。**
Runtime 的"当前时间"必须作为参数**注入**，绝不在内部直接读 `now()`。否则无从谈确定性，也无法测试与重放。时区 / DST 的处理同样显式化。

**E4 — Run 可重放（Replayable）、可验证（Verifiable）。**
**确定性的精确定义**：给定「同一 Flow 定义 + 同一注入时钟序列 + 同一 Run 事件日志（含暂停/跳过/确认等现实中断）」，必产生**相同的事件序列**。
现实中断被纳入"输入"，因此 C5（现实优先）与"可重放"不冲突，反而互补。Run 的重放日志同时是模块重构的黄金主测试（见 C10）。

**E5 — Flow 格式开放、可读、可版本化。**
- 每个 Flow 携带 **schema 版本号**；格式只能**加法演进**或提供迁移，绝不做破坏性变更——否则分享出去的 Flow 会在升级后损坏，违背 C6。
- 格式必须人类可读、可 diff（利于 Git、AI、用户三方理解）。

**E6 — 描述性，永不处方性（尤其医疗场景）。**
创始场景是患者护理。分享一个用药 Flow 近似医疗建议，出错会伤人。因此：
- Flow 是**描述性**的，**永不构成医疗处方或诊断**。
- 分享的健康类 Flow 必须携带**来源（provenance）**与免责声明。
- App 不得把他人分享的用药表呈现为权威指令；用户对自己的健康决策负责。

## B. 可修订的实现选择

这些是当前的最佳判断，会随经验演进，改动无需走 ADR：

- **v1 只用一种规范格式**：优先 JSON（机器友好）配合良好命名的 schema，或 YAML（更易读）。二选一，先跑起来。
- **暂不自研 DSL。** 同时维护"DSL + JSON + 转换层"是典型的过早复杂化（违反 Constraint 0）。等核心模型被真实用户验证后，再评估是否引入人类可读 DSL。
- **存储**：本地优先（离线可用），后续再加同步。具体后端待定。
- **UI/客户端技术**：见 `docs/architecture.md`（当前为 Expo / React Native）。
