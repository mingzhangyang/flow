# 领域模型

本页定义产品的核心概念。它们是**不可变原则**：其他一切（UI、存储、AI、通知）都建立在这几个概念之上。

## 一、Flow（定义）≠ Run（运行实例）

这是全系统最重要的一条区分。"Flow"这个词其实指两个不同的东西，必须分开：

| | **Flow（定义）** | **Run（运行实例）** |
|---|---|---|
| 是什么 | 一份可复用的时间模式**模板** | 某一次具体执行 |
| 可变性 | **不可变**（编辑产生新版本） | 携带运行状态（当前步、暂停、跳过） |
| 声明式? | 是，只描述"应该发生什么" | 记录"实际发生了什么"（事件日志） |
| 作用对象 | 分享、导出、版本化 | 暂停/恢复/跳过/回退、重放、验证 |

**推论（这条区分自动满足多条约束）：**

- **C5（暂停/跳过）只作用在 Run 上**——现实世界的混乱都装进 Run，不污染定义。
- **可重放/可验证只针对 Run 的事件日志**，而不是定义（见 `03-engineering.md`）。
- **AI-C1（AI 不能修改正在运行的 Flow）天然成立**——运行的是 Run 的定义快照，AI 编辑的是 Flow 定义。
- 分享一个 Flow，分享的是知识；不会把你昨晚做饭的中断状态一起带出去。

## 二、两种时间拓扑（都是一等公民）

节点之间的关系不止一种。产品必须同时支持，且不能为了塞进其一而破坏另一：

**1. 顺序型 / 相对（Sequential）** —— 事件串成链，"下一件事是什么"，计时从上一步结束向前推。
典型：法压咖啡、实验步骤、菜谱。C3 完美契合。

**2. 日程型 / 绝对（Scheduled）** —— 事件钉在墙钟时间上，**可重复**（如每天 8:00 / 14:00 / 20:00），且多个事件**可并行、互相独立**。
典型：患者按时服药（创始场景）。此时往往**没有单一的"下一件事"**——多颗药各自独立，漏服一颗不阻塞另一颗。

> 设计红线：不要假设 Flow 总是"一条线性时间线"。核心模型必须容纳"一组可并行的定时事件"。任何强行把日程型压成顺序型的设计，都会破坏创始场景。

## 三、Node（节点）

一个节点表达**一个事件**（C3），最小词汇表要小而封闭（新增节点类型须按 Constraint 8 追溯到宪章）。v1 认可的节点类型：

- **计时步骤（Timed）**：有持续时长的动作（浸泡 4 分钟）。
- **绝对时刻（Scheduled）**：钉在墙钟时间上的事件（每天 8:00 服药）。
- **手动确认（Gate）**：等待用户确认后才继续（C5：等待确认）。
- **瞬时动作 / 检查点（Instant）**：无时长的一步（"压杆"）。
- **并行组（Parallel）**：一组互相独立的子事件。

其余（分支 Branch、循环 Repeat 等）暂不进入 v1；引入时必须先回答它满足哪一条 Constraint。

**每个节点除了"做什么"，还可携带"为什么"（rationale）。**
这正是 Flow 从"配置"升为"知识"的关键（C2 + AI-C2）：
"等待 5 分钟 —— *因为黄油需要时间融化*"。rationale 是可选字段，但模型必须为它留出位置。
